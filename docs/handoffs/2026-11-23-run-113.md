## Engineering change

The Cosmos-native auth service now treats cancellation consistently at the final in-process boundaries before durable state writes:

1. Registration rechecks cancellation after PBKDF2 derivation and before transactional batch execution.
2. Login rechecks after password verification, including the invalid-password path, before refresh-token rotation.
3. Refresh and logout recheck before their ETag-conditional writes after identity hydration.
4. A non-success registration batch response rechecks cancellation before translating it to conflict or storage-unavailable.
5. A successful transactional batch response remains authoritative after commit; a late request cancellation does not misreport a committed registration as failed.

Eight deterministic test cases cover registration batch-preparation cancellation, non-success batch response mapping, successful committed registration after late cancellation, login cancellation for both valid and invalid passwords, and refresh/logout cancellation during identity hydration.

No API endpoint, OpenAPI contract, schema, fare, agreement, ride, dispatch, FIFO or customer-facing workflow behavior changed.
